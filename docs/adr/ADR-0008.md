# ADR-0008: Scoped Firestore Listener Recovery

## Status

Accepted

## Date

2026-07-29

## Context

### Original Issue
Immediately after an artifact was published, authors frequently observed that player metadata (reaction counts, resonance status) remained frozen or stale. This was traced to a `PERMISSION_DENIED` error from Firestore when attaching a listener via `ArtifactRepository.observeArtifact()`.

### User Impact
Authors experienced a "disconnected" state for their newly shared content, creating doubt about the publishing success and requiring manual playback restarts to "fix" the UI.

### Verified Behavior
The investigation (FIRESTORE-REC-2026-001) verified that the error is caused by a race condition: the local Single Source of Truth (Room) transitions to the `PUBLISHED` state faster than Firestore's backend eventual consistency or the client SDK's internal authentication state synchronization. While the server-side write completes successfully, the document is transiently unreachable for a window of 100ms–2000ms.

### Architectural Constraints
*   The `ArtifactRepository.observeArtifact()` API contract (returning `null` on error) must be preserved to avoid global regression risk.
*   Security rules must not be loosened to "fix" a timing issue.
*   Recovery must be deterministic, bounded, and narrowly scoped to the publishing transition.

## Decision

We have implemented a transition-aware recovery mechanism in the domain layer (`GetPlayerContextUseCase`).

### Key Components:
1.  **Transition Detection**: Used the `scan` operator in the metadata pipeline to detect the specific moment an artifact transitions from `isDraft == true` to `isDraft == false`. This identifies the high-risk "just published" window.
2.  **Internal Exception Signal**: Transformed the repository's `null` emission (representing the denial) into a private `TransientPublishingException` ONLY when the `wasJustPublished` signal is active.
3.  **Bounded Retry**: Applied `.retryWhen` to the metadata flow with a maximum of **3 attempts** and a **2-second linear delay**.
4.  **Graceful Settlement**: Added a terminal `.catch` block to ensure that if all retries fail, the flow settles back into a `null` state, matching the existing "silent failure" behavior and allowing the player to remain functional using local data.

## Alternatives Considered

### 1. Repository-Level Retry
*   **Rejected**: Widens the failure domain. Every consumer of `observeArtifact()` would inherit retry behavior, potentially masking genuine permission violations or creating duplicate listener pressure across the app.

### 2. Global Retry Policy
*   **Rejected**: Violates "Zero-Trust" principles. Retrying every permission failure is inefficient and delays the delivery of legitimate security errors to the UI.

### 3. PlaybackSessionManager Re-emission
*   **Rejected**: High regression risk. Forcing the playback coordinator to emit a new `Artifact` instance could trigger unintended UI flickers, playback resets, or redundant analytics events.

### 4. Repository Exception Propagation
*   **Rejected**: Modifying the repository contract to throw exceptions instead of emitting `null` would require refactoring every collector in the codebase, introducing significant architectural churn for a localized timing issue.

## Consequences

### Positive
*   **Encapsulation**: Recovery logic is strictly contained within the domain layer where the business rule (publishing window) is defined.
*   **Stability**: The repository API remains stable for all other features (Feed, Library, etc.).
*   **Surgical Precision**: Retries are only triggered during the verified publishing window for the active artifact.
*   **Self-Healing**: The UI automatically resolves transient denials within seconds without user intervention.

### Negative
*   **Latency**: In rare cases of extreme Firestore lag (>6s), the metadata may still settle into a stale state until manual restart.
*   **Complexity**: Increases the complexity of the UseCase reactive pipeline by adding stateful memory (`scan`).

## Verification

*   **Unit Testing**: `GetPlayerContextUseCaseTest` covers transition detection, bounded retry exhaustion, track change cancellation, and isolation from feed playback.
*   **Runtime Verification**: Verified on emulator/device that `PLAYER_TRANSITION_PUBLISHED` and `ARTIFACT_OBSERVE_RETRYING` logs appear as expected and recovery succeeds.
*   **Production Monitoring**: Defined KPIs for recovery rate and retry effectiveness to be monitored during rollout.

## Lessons Learned
*   **Consistency Lag**: Success in a `await()` write call does not guarantee immediate read consistency for subsequent listeners.
*   **Reactive State**: The `scan` operator is the correct pattern for implementing session-aware logic in stateless reactive streams.
*   **Defensive Recovery**: Surgical retries using specific internal exceptions allow for robust recovery without degrading the system's overall security enforcement.
