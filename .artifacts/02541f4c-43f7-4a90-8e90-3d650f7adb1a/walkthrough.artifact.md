# Production Readiness Investigation: Finding #3 – Main Thread Disk I/O

This walkthrough documents the static code analysis performed to evaluate the production risk of main-thread disk I/O operations.

## Problem Statement

The application performs several filesystem operations (metadata checks and file manipulation) on the Main thread. The most critical occurrence is a high-frequency (50ms) heartbeat loop in the `RecordingService` that checks available storage using `StatFs`.

## Question Being Answered

**Does the application perform disk I/O on the main thread in a way that can realistically cause dropped frames, UI jank, or ANRs?**

**Answer**: Yes. The current implementation of the recording heartbeat loop performs a disk-accessing system call (`StatFs`) every 50ms on the Main thread. This frequency is high enough to cause significant UI impact if the disk is busy.

## Evidence Collected

### 1. High-Frequency `StatFs` in Heartbeat Loop
In [RecordingService.kt](file:///F:/Android%20Project/01/app/src/main/java/com/saurabh/artifact/audio/RecordingService.kt#L456-L476), the `startTimer` function launches a coroutine on `Dispatchers.Main` (via `serviceScope`) that executes every 50ms:

```kotlin
// F:/Android Project/01/app/src/main/java/com/saurabh/artifact/audio/RecordingService.kt
private fun startTimer() {
    timerJob?.cancel()
    timerJob = serviceScope.launch { // Launched on Dispatchers.Main
        // ...
        while (isActive) {
            delay(50.milliseconds)
            // ...
            if (_recordingState.value.status == RecordingStatus.RECORDING) {
                // ...
                // Storage Monitoring
                val availableMb = storageManager.availableStorageMb // BLOCKS MAIN THREAD
                // ...
            }
        }
    }
}
```

The `availableStorageMb` implementation in [StorageManager.kt](file:///F:/Android%20Project/01/app/src/main/java/com/saurabh/artifact/util/StorageManager.kt#L34-L42) uses `StatFs`:

```kotlin
// F:/Android Project/01/app/src/main/java/com/saurabh/artifact/util/StorageManager.kt
val availableStorageMb: Long
    get() = try {
        val stats = StatFs(context.filesDir.absolutePath) // statvfs system call
        val availableBlocks = stats.availableBlocksLong
        val blockSize = stats.blockSizeLong
        (availableBlocks * blockSize) / (1024 * 1024)
    } catch (e: Exception) { ... }
```

### 2. Service Lifecycle Disk I/O
Several service actions in `RecordingService.kt` perform disk operations on the Main thread:

- **[stopRecording](file:///F:/Android%20Project/01/app/src/main/java/com/saurabh/artifact/audio/RecordingService.kt#L416-L454)**: Calls `capturedFile.exists()`, `capturedFile.length()`, and `capturedFile.delete()` on the Main thread.
- **[cancelRecording](file:///F:/Android%20Project/01/app/src/main/java/com/saurabh/artifact/audio/RecordingService.kt#L389-L414)**: Calls `file.exists()` and `file.delete()` on the Main thread.
- **[startRecording](file:///F:/Android%20Project/01/app/src/main/java/com/saurabh/artifact/audio/RecordingService.kt#L236-L311)**: Calls `storageManager.isStorageAvailable()` on the Main thread.

## Analysis

| Execution Path | Frequency | Thread | Severity | Impact |

## Findings

> [!IMPORTANT]
> **Finding #3 is a Verified Production Risk.**
>
> The heartbeat loop in `RecordingService` is the primary concern. Executing `StatFs` at 20Hz on the Main thread is a textbook cause of "micro-jank" and potentially severe frame drops if the Android system is under I/O pressure (which is common during file writing, such as the recording itself).

- **Confidence Level**: Level 2 – Code Evidence
- **Status**: **OPEN**

## Recommendation

1.  **Throttle Storage Checks**: Reduce the frequency of `availableStorageMb` checks. Checking once every 5-10 seconds is likely sufficient for storage monitoring.
2.  **Offload to `Dispatchers.IO`**: Move the storage check logic in `RecordingService` to an IO-bound context.
3.  **Update Repositories**: Ensure all `File.exists()` and `File.length()` calls in `RecordingService` are moved to `withContext(Dispatchers.IO)`.
